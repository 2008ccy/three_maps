## 一、选题说明与三图总览

### 1.1 我们研究什么，帮助谁理解什么

**选题：从预训练模型到领域助手——语言模型的数据、微调、评测与部署。**

读者是希望理解“一个聊天模型怎样成为有依据的课程助手”的大一同学。我们解释模型适配的全过程，以及每个阶段应学什么、使用什么工具、怎样判断有效。成长方向以 AI 工程师的系统实现为主，同时保留科学家的证据意识和设计师对真实使用体验的关注；不要求成员现在确定职业。

**典型任务：把已有语言模型与经授权的课程资料结合，构建课程答疑助手。** 输入是同学的问题及必要的上下文，输出是通俗解释、资料出处和下一步学习建议；找不到依据时说明不足，问题不清时先澄清。具体服务哪门课、允许使用哪些课件，由小组与教师确认。

**研究边界：**重点讨论资料准备、分词与模型原理、RAG、SFT/LoRA、评测和部署。预训练与分布式训练作为背景；图像生成、机器人、从零训练大型模型不作为本次交付主体。训练实验根据资源选做，网站必须实现一项真正服务地图的 AI 能力。

## 二、领域地图

<a id="task-qa"></a>
### 2.1 主要解决什么问题，有哪些典型任务

语言模型领域包含语言生成、信息抽取、语义表征与检索、指令跟随及行为对齐。课程助手主要使用其中四类能力：

| 任务 | 输入与输出 | 课程中的用途 | 怎样检查 |
| --- | --- | --- | --- |
| 概念解释与对话 | 问题→解释或追问 | 用适合初学者的语言解释术语 | 正确性、表达清晰度、是否满足问题 |
| 语义检索 | 问题→相关资料片段 | 找到相关章节与原始依据 | 检索命中、片段是否完整 |
| 摘要与比较 | 指定材料→总结或差异 | 比较 RAG 与 LoRA、整理学习路线 | 是否遗漏条件、是否忠于材料 |
| 引用、澄清与拒答 | 问题和证据→带出处回答或说明未知 | 资料缺失时避免编造课程事实 | 引用是否支持结论、拒答是否恰当 |

这些功能共同服务“帮助同学理解并追溯依据”的目标。回答更长、模型参数更多、消耗 token 更多，都不能单独证明任务完成得更好。[L3、L5]

### 2.2 一个典型任务怎样完成

| 步骤 | 具体工作 | 应保留的产物 | 常见失败与排查 |
| --- | --- | --- | --- |
| 1 定义任务 | 明确课程、读者、可答范围、引用方式与失败代价 | 任务卡、样例问题、验收标准 | “什么都能答”导致边界不清，先缩小范围 |
| 2 准备资料 | 获取授权，解析文本，保留页码/章节；清洗和去重 | 资料清单、来源 ID、数据版本 | 公式解析错、页码丢失，回看原文 |
| 3 建评测集 | 从真实学习困难出题，包含有答案、无答案和模糊问题 | 题目、评分要点、支持片段 | 同一题泄漏到训练和测试，按来源分开检查 |
| 4 跑基线 | 同时保留“只检索原文”“模型直接答”“检索后答” | 固定设置及回答记录 | 不同模型、提示和问题混用，无法归因 |
| 5 做 RAG | 分块→建立索引→检索/可选重排→把片段交给模型 | 片段与索引版本、召回记录 | 没找到正确资料时，先修检索而非换大模型 |
| 6 决定是否微调 | 仅在有稳定的格式/行为问题、样本和资源时尝试 SFT/LoRA | 训练配置、数据切分、适配器 | 测试集调参、只看训练 loss，结论不可信 |
| 7 整体评测 | 查内容、引用、拒答、时延、成本和失败类型 | 对照表、错误案例、局限 | 只报一个平均分，掩盖无答案题乱答 |
| 8 部署和更新 | 前端展示；服务端调 API；记录反馈并修订 | 公开网址、更新记录、反馈处理 | 开发电脑关机后失效、引用打不开 |

可以先用关键词检索或 BM25，再判断是否需要向量检索。资料少时，无需先搭建复杂向量数据库；方法优劣以本组任务评测为准。RAG 的原始研究将检索得到的外部记忆与生成模型结合，本项目采用其“检索依据后再生成”的应用思路，不声称复现原论文全部训练设计。[S02]

### 2.3 核心概念与原理分别解释什么

| 节点 ID | 概念 | 通俗解释与任务作用 | 关系或边界 | 来源 |
| --- | --- | --- | --- | --- |
| K-TOKEN | Token 与分词 | 把文字转换为模型可处理的单位；影响输入长度与计费 | token 不固定等于一个汉字或一个单词 | L3、S07 |
| K-EMBED | 嵌入 | 把文本表示成向量，使相似度计算成为可能 | 相似不等于事实正确；可服务检索 | L3、S02 |
| K-TRANSFORMER | Transformer 与注意力 | 利用位置信息和相关性聚合上下文 | 是模型结构；本身不保证引用或事实正确 | S01 |
| K-PRETRAIN | 预训练 | 从大量数据学习语言模式与知识 | 是适配的基础，不作为本组大规模实验 | L3、S07 |
| K-SFT | 监督指令微调 | 用问题与示范回答继续训练模型的输出行为 | 是训练任务；可全参训练，也可结合 LoRA | S06 |
| K-LOSS | 交叉熵与泛化 | 交叉熵衡量目标 token 的预测损失；泛化关心未见样本 | loss 下降不能替代下游答疑评测 | L3、L5 |
| K-LORA | LoRA | 冻结基座权重，用可训练的低秩增量适配模型 | 重点减少可训练参数，不使整套训练免费 | S03、S05 |
| K-QLORA | QLoRA | 在量化冻结基座上训练低秩适配器，节约显存 | 实际训练还需激活、梯度与其他状态 | S04 |
| K-RAG | 检索增强生成 | 先找资料，再让模型结合资料回答 | 可更新资料；仍会出现检索错或生成错 | S02 |
| K-EVAL | 评测与数据泄漏 | 用独立题目检查真实任务质量 | 公开榜单与课程自建评测互补 | S09、L5 |
| K-DEPLOY | 推理与部署 | 把模型/API 接成可访问的服务 | 网站托管、模型推理、训练是三种资源需求 | L2、S10 |
| K-CARD | 数据卡与模型卡 | 记录来源、用途、版本、限制和责任边界 | 帮助他人判断是否适合复用 | L3 |

四个用于理解方法的公式：

- 语言建模交叉熵：$L=-\frac{1}{T}\sum_{t=1}^{T}\log p(x_t\mid x_{<t})$，表示预测真实后续 token 的平均损失，不能直接衡量教学价值。
- 缩放点积注意力：$\operatorname{Attention}(Q,K,V)=\operatorname{softmax}(QK^\top/\sqrt{d_k})V$，先计算相关性，再聚合信息。[S01]
- LoRA：$W'=W+\frac{\alpha}{r}BA$，训练低秩增量而非完整的 $W$；秩 $r$ 是待选择的超参数。[S03]
- API 成本：$C=(T_{\mathrm{in}}P_{\mathrm{in}}+T_{\mathrm{out}}P_{\mathrm{out}})/10^6$，其中单价单位为元/百万 token。实际还要计入检索、缓存、推理模式等项目适用的费用。[S21]

<a id="route-choice"></a>
### 2.4 方法之间是依赖、替代还是协同

| 路线 | 解决什么 | 与其他路线的关系 | 什么时候采用与主要局限 |
| --- | --- | --- | --- |
| 提示与上下文示例 | 说明任务、格式和回答边界 | 是低成本基线，也能与其他方案组合 | 先试；不能仅靠提示补齐缺失知识 |
| RAG | 按问题提供可更新的外部资料 | 与微调互补；与长上下文部分替代 | 需要引用、课程知识经常变化时优先试；依赖检索质量 |
| SFT | 学习示范回答的行为模式 | 依赖已有模型和样本；可用全参或 LoRA 实现 | 格式和引导方式持续不合适时考虑；存在过拟合和能力回退 |
| LoRA/QLoRA | 在受限资源下实现模型适配 | 是 SFT 等训练的参数/显存方案，不与 SFT 平级互斥 | 有可用设备和合格样本时再做；兼容性、序列长度影响资源 |
| 全参数微调 | 更新全部模型参数 | 与 LoRA 是不同的适配方案 | 可作比较背景；本组缺乏资源时不强行执行 |
| 偏好优化 | 调整偏好、回答行为 | 通常在已有模型与数据基础上进一步开展 | 自主拓展；不作为第一版依赖 |
| 蒸馏与推理量化 | 降低推理资源需求 | 可与已适配模型协同使用 | 确实需要自托管推理时评估；要重新测质量 |
| 工具调用/Agent | 获取信息或执行动作 | 可与 RAG 组合 | 只有问答需要行动时才加，需处理权限与错误传播 |

**本组路线判断：**先用授权资料和 API 完成可引用问答；若错误来自找不到资料，先改解析、切块和检索；若资料已找对但输出行为持续不符合要求，再评估 LoRA。是否“微调优于 RAG”不能脱离任务、数据与预算作绝对判断。[分析判断；S02—S06]

### 2.5 软件、模型与框架能做什么，依赖什么

| 工具/对象 ID | 在任务中的作用 | 相关概念与前置知识 | 学习入口 | 局限或替代 |
| --- | --- | --- | --- | --- |
| T-PYTORCH | 张量、自动求导与训练循环 | Python、矩阵、梯度；K-LOSS | S08；后续机器学习基础 | 大一先做小例子；网站调用 API 不需要装训练环境 |
| T-TRANSFORMERS | 加载 tokenizer、模型与训练/推理接口 | K-TOKEN、K-TRANSFORMER | S07；CS224N 自主拓展 | 必须查具体模型兼容性；不是所有模型都可直接运行 |
| T-PEFT | 给基座添加 LoRA 适配器 | K-LORA、微调流程 | S05；读 LoRA 论文 | 不提供课程数据质量保证，也不自动完成评测 |
| T-TRL | 组织 SFT 等后训练过程 | K-SFT、训练样本与配置 | S06 | 第一版可不用；版本、模板和损失设置需固定 |
| T-RETRIEVAL | 关键词/向量检索和证据排序 | K-EMBED、K-RAG | S02；先理解索引和切块 | 关键词方案先跑通；FAISS 等只解决检索中的一部分 |
| T-EVAL | 用固定设置运行基准或自建题 | K-EVAL、评分与统计 | S09；本节评测方案 | 通用题库不能替代课程问题与人工检查 |
| T-VLLM | 自托管场景的模型推理服务 | K-DEPLOY、显存和并发 | S10；后续系统学习 | 普通网站 CPU 主机不等于合格模型服务器；第一版用 API |
| T-OLLAMA | 本地运行兼容模型的尝试入口 | 模型大小、量化与机器资源 | L4 中的实践线索；具体模型需查官方说明 | 易启动不等于所有机器都流畅；网站不依赖成员电脑 |
| M-BASE | 已发布的指令语言模型 | K-TRANSFORMER、K-SFT | 模型卡、官方示例；S11 是历史案例入口 | 最终型号、revision、许可和 API 模型 ID 待选定，不写成“最新最强” |

重要工具的关联链是：**课程答疑任务→RAG/LoRA 等方法→检索或训练工具→需要的知识→课程或教程→可验收实践。** 例如，PEFT 不只是一个仓库名，它连接 LoRA、低秩矩阵、监督微调、同一测试集上的前后对比和适配器产物。

### 2.6 需要什么数据、评测与硬件

**数据。** 第一批数据用经授权的课程讲义、教学大纲、教材节选及人工核对的问答。每份资料记录作者、许可/使用范围、章节、时间、版本和来源链接；不将完整受限课件直接公开。Common Crawl、The Pile 等只作为预训练背景，不是完成本次作业必须下载的数据。

**评测。** 建议从 30 道真实问题起步，再扩展到 50—100 道。这是项目建议数量，不是作业指定指标。题目至少覆盖概念解释、关系比较、资料定位、无答案和模糊问题；训练、调参与最终测试分开。评价时同时记录：

| 维度 | 操作定义 | 记录方式 |
| --- | --- | --- |
| 答案正确性 | 按预先写好的要点，是否正确且不遗漏关键条件 | 每题 0/1/2 分并记录判分理由 |
| 引用支持率 | 所引用的片段是否确实支持对应结论 | 支持的引用数/检查的引用数，同时给出分子分母 |
| 检索表现 | 标注的支持片段是否进入前 k 条结果 | 记录 k、命中题数和总题数 |
| 无答案处理 | 无依据时是否恰当拒答或要求补充 | 单列无答案题的结果，检查过度拒答 |
| 使用体验 | 同学是否能理解，并找到原文和后续入口 | 独立试用记录与具体问题 |
| 时延和成本 | 端到端耗时、输入输出 token 和费用 | 小样本报逐条数据/中位数；量足够后再看 P95 |

不要为了凑指标使用无来源的“90%准确率”或“4秒内完成”；先跑基线，再确定本组目标。自动模型评分可以辅助归类，评分规则和抽样人工复核仍由小组负责。

**资源。** 网页交互、内容整理和调用模型 API 可用普通笔记本开发。公开网站用托管平台；AI 推理由提供方执行，本组按使用付费。训练实验另用可获得的学校 GPU 或短租 GPU，先小模型、小样本、小批量试跑。不能用“7B 权重约占若干 GB”代替整套训练显存估计，序列长度、激活、优化器和运行框架都会影响峰值。[L2、S04]

### 4.2 案例 A：训练 loss 下降，是否说明回答更好

**具体问题。** 指令微调后训练 loss 下降，可以宣布课程答疑质量提升了吗？

**使用的方法。** 系统拆解：把训练目标、对未见题的泛化、引用正确性和学习体验分开；再寻找“训练指标改善但真实任务不改善”的反例。

**依据与比较。** loss 衡量所选目标上的预测误差，课程答疑还要求事实准确、引用成立、解释清晰和恰当拒答。过拟合、数据泄漏、样本范围狭窄、评分错位都可能使训练 loss 失去代表性。验证 loss 上升是一种警讯，但即使训练与验证 loss 都下降，也仍可能出现下游质量不改善。[L3、L5；S06]

**当前判断。** 只有在固定模型版本、同一独立测试题与同一评分规则下比较训练前后回答，才可判断对本任务是否有效。loss 曲线、下游评分与错误样例应一起解释；不把它们写成必须全部严格同向的机械规则。

**本组如何检验。** 有训练资源时固定小样本配置，保存配置、种子、训练/验证曲线、前后同题回答、人工判分和至少一个失败案例；没有训练条件时，完成文献对比与具体回答分析，并清楚标为文献分析，不能声称跑过训练。

**尚存疑问。** 本组尚缺真实曲线、测试回答与判分记录；小样本改善能否泛化、是否损害无答案拒答能力，需要后续检验。

跨图连接：K-LOSS→K-SFT→T-TRL/T-PEFT→独立测试→本案例。

### 4.3 案例 B：通用榜单靠前，就适合课程答疑吗

**具体问题。** 能否直接选通用 benchmark 排名靠前的模型作为课程助手？

**使用的方法。** 对照比较，先定义“适合”的含义，再控制问题、资料、提示、输出长度和评分条件。

**依据与比较。** 通用题库用于测量其定义的能力，课程答疑还要求对本课术语、指定资料与读者水平作恰当回应。知识覆盖、污染、提示设置和评分方法均会影响榜单表现；检索配置不同，也会使“模型比较”变成“系统比较”。[L5、S09]

**当前判断。** 榜单只作初筛；最终以本课程测试题、支持引用、无答案处理、时延和成本决定。若比较不同完整系统，应明确这样命名，不把差异全部归于模型大小。

**本组如何检验。** 从同一批授权资料出题，设置直接问答与检索后问答两组条件；保存模型 ID、版本/日期、提示、检索结果和回答。至少两位成员先按同一评分细则独立评分，再讨论分歧。可以从 10 题探索开始，正式评价使用另留的测试题。

**尚存疑问。** 最终目标课程、模型候选、标准答案与评分细则待确定；当前没有可报告的胜率或准确率。

跨图连接：K-EVAL→T-EVAL/E-ELEUTHER→课程自建题→本案例→模型选型。

### 4.4 案例 C：准确、速度与成本怎样取舍

**具体问题。** 大一小组应购买 GPU、租服务器运行模型、做 LoRA，还是先调用 API？

**使用的方法。** 多目标取舍，同时考察学习目标、准确性、时延、费用和维护负担，借助方法演进分析解释低成本适配的动机。

**依据与比较。** 全参微调更新全部参数；LoRA 减少可训练参数；QLoRA 进一步利用量化基座；RAG 则提供外部资料，可以与微调共存。它们改变不同环节的代价，不能简单按“谁最高级”排序。网站服务器与训练设备也应分别决策。[S02—S04、L2]

| 选择 | 对本组的收益 | 主要代价 | 当前判断 |
| --- | --- | --- | --- |
| API＋资料检索 | 无需部署模型即可验证课程答疑和地图 AI | 调用费用、供应商与网络依赖 | 第一版优先 |
| 本地兼容小模型 | 便于理解推理、减少部分外发依赖 | 受设备内存、速度与格式兼容限制 | 作为单独学习实验 |
| LoRA/QLoRA | 学习真实适配流程 | GPU、数据、训练和评测投入 | 在基线和评测形成后再决定 |
| 自建 GPU 推理服务 | 可控性较强 | 购置/租赁、并发、运维和闲置成本 | 无明确需求和预算时不作为作业起点 |

**当前判断。** 沿用建设计划中“网站调用外部 API、训练单独安排”的分工，并将网站维护简化为托管前端和一个接口。小模型配合合格资料可能更适合本任务，但仍需实测，不能提前写成结论。

**尚存疑问。** API 型号和真实调用价、访问量、检索效果及本组可用设备未确定。现有“7B 从14GB降到4GB”的素材表述不足以证明可在4GB显存内完成训练，本文不采用该保证。

### 6.2 至少一项 AI 能力怎样直接服务地图

**第一版功能：基于地图材料回答“RAG 与 LoRA 怎么选”“学 LoRA 先补什么”“这个判断有什么依据”。**

请求流程：浏览器提交问题/节点ID→后端从已发布且核实通过的内容中检索节点、关系和来源片段→模型只根据给定材料解释→返回答案、节点ID和来源ID→页面展示可点击引用。

小规模地图可以先用关键词及类型筛选检索，再按需要升级；不要求先做向量数据库。模型返回的引用ID必须属于本次提供材料；程序应拒绝未知ID，成员还要抽查引用是否真的支持结论。AI 输出不直接写回正式地图。

服务端保存模型密钥，访客无需提供个人密钥。不能把密钥放入公开仓库、浏览器脚本或前端构建变量；GitHub Actions 中保存了 Secret，也不代表编译进浏览器的内容会保密。接口限制问题长度、输出长度与调用量；材料不足、超时或预算用尽时明确提示，地图浏览仍可用。

### 6.3 内容怎样持续更新

每周至少检查一次：官方项目变更→与本题有关的线索→成员核实→修改节点/关系/案例→写明依据与原因→复核发布。没有值得修改的内容时，记录“已检查、暂无需修改”及检查范围。

更新记录格式：`日期｜对象ID｜原内容→新内容｜依据｜原因｜负责人｜复核人`。自动抓取和 AI 整理只能进入待核实区。Git 提交保存版本历史，网站上仍需有同学看得懂的更新说明。

### 6.4 怎样证明云端公开可用

必须关闭开发电脑后再次访问；浏览无需登录或逐人申请权限；在非组员电脑与手机、校园网与移动网络上检查三图、来源、跨图、AI和反馈。至少三名非组员各自完成真实任务，保留问题与处理结果。域名、托管和 API 服务要覆盖互评及期末时间。

仅展示录屏、仅把 Markdown 放进 GitHub、仅提供有时效或需要权限的预览链接，都不能代替这个验收。

## 七、GitHub 是否够用，以及适合大一的方案

### 7.1 可以用 GitHub，但需要分清它承担什么

**可以用 GitHub 构建交互网站，不需要因为“动态交互”四个字就放弃它。** GitHub 仓库负责源码、内容和版本；Pages 发布 HTML/CSS/JavaScript，浏览器中的 JavaScript 可以实现搜索、筛选、节点点击、关系展示和跨图跳转。内容文件修改后重新发布，也满足人工持续更新的技术需要。

但 **GitHub Pages 本身不运行常驻后端应用、数据库或模型代理**。受保护的 AI 调用、统一写入反馈等功能需要外部服务；官方文档也明确 Pages 不支持服务端语言运行。不要将 GitHub Actions 或 Codespaces 当作给全班长期访问的生产服务器。[S15、S16]

| 作业功能 | 只用 GitHub Pages 是否可做 | 补充条件 |
| --- | --- | --- |
| 三图、搜索、筛选、节点详情与来源 | 可以 | 前端脚本与内容文件 |
| 每周改内容、留下版本与网站更新说明 | 可以 | 成员编辑文件并重新发布 |
| 公开 AI 问答且隐藏密钥 | Pages 单独不够 | 另有服务端/云函数代理 |
| 将所有人的反馈存到共同位置 | Pages 单独不够 | 外部表单或后端存储；浏览器本地存储不等于共享数据 |
| 成员在网页中登录并编辑发布 | Pages 单独不够 | 需鉴权与可写后台；本作业第一版可改用 Git 文件维护 |
| 国内普通网络持续可访问 | 不能从“部署成功”直接认定 | 必须实测最终地址与全部核心资源 |

因此，GitHub Pages 适合前端演示和备用镜像。为满足这次作业，推荐仍把 GitHub 留作协作与版本中心，公开站点交给能运行函数的托管平台。

### 7.2 推荐的低维护方案

**推荐组合：GitHub＋简单前端（原生 JavaScript，或组员熟悉的 Vite/React）＋EdgeOne Pages＋一个服务端 AI 接口＋自有域名。** 原计划中的 Next.js＋SQLite/Prisma＋Docker＋Caddy 可以作为后续升级；第一版用托管服务代替自管服务器，用 JSON/Markdown 文件代替数据库和成员后台。

```text
组员修改内容/代码 → GitHub 审阅与版本记录 → 托管平台构建发布
                                              ↓
同学浏览器 → 自有域名 → 三张地图、搜索、来源与更新记录
                         └→ 服务端 AI 接口 → 选定的模型 API

同学反馈 → 可匿名外部表单 → 成员核实 → 修改内容并记录理由
```

EdgeOne 官方材料提供 Git 集成、托管与函数能力，并有免费用量套餐；函数、构建和存储等仍有配额，应以控制台当时显示为准。[S17、S18] AI 接口可以由 Pages Functions 读取服务端环境变量并调用外部模型。[S19] 部署前验证所选函数运行时的联网、超时、地域和流式响应支持，不能只凭前端能打开就认定 AI 完成。

**域名要作为正式交付条件准备。** 当前 EdgeOne 中国站文档说明：默认项目/部署域名在部分区域依赖有效期3小时的预览链接；全球不含中国大陆区域的默认域名对中国大陆网络返回401。因此不能用默认预览地址交作业，需绑定自定义域名；加速地域、备案条件及校园网访问要另行核对。[S20]

最省流程的候选是自有域名＋全球不含中国大陆区域，再用真实校园网络检查；**这只是减少接入流程的候选，不保证国内访问质量**。如果不稳定，改用学校提供的公开托管环境，或走中国大陆区域及平台要求的域名备案流程。接入要求以平台与官方说明为准，不把“全球节点”写成“国内稳定”。

反馈先用无需登录的表单，管理员手动整理处理结果后公开摘要；发布前用非组员浏览器验证表单真的可匿名提交。不要为第一版写整套用户系统。若后续必须在线多人编辑，再评估托管数据库与权限，不将函数本地文件当作可靠持久化数据库。

| 1 内容先闭环 | 从本文挑核心节点和有依据关系，整理成 JSON；保留来源与待核实状态 | 从RAG能查到任务、工具、研究团队、课程入口和案例 |
| 2 做可浏览前端 | 首页、三图入口、详情、搜索与跨图；手机列表 | 同学不听讲解能走完一条路径 |
| 3 尽早试部署 | 导入仓库或上传构建产物，准备自有域名并验证网络 | 正式地址公开可访问，不依赖临时预览或开发电脑 |
| 4 加一项AI | 一个服务端接口、地图检索、引用、未知处理与调用限制 | 三类问题可演示：有依据、无依据、路线比较 |
| 5 加更新与反馈 | 网站更新页，外部表单或轻量反馈接口 | 能看到一次反馈核实和处理的完整记录 |
| 6 做外部验收 | 三名非组员独立访问，记录设备、网络、任务和问题 | 核心问题修复，剩余局限明确 |

最小目录示意：`src/`放交互；`content/nodes.json`、`edges.json`、`sources.json`放地图；`updates.md`放更新说明；函数目录按平台当前文档放 AI 接口。第一版无需管理员登录、复杂数据库、自动爬新闻或自托管语言模型。

若必须立即沿用原计划，也可以采用云服务器方案，但要承担 Linux、HTTPS、备份、部署和故障恢复。对目前以材料整理为主的小组，先做上述托管方案的维护负担更小；不是因为大一不能学服务器，而是这些运维工作尚未直接增加地图内容与认识质量。

### 9.3 对三份素材作出的整理与修正

1. 将宽泛“AI模型构建”收束为既定的课程答疑任务；保留预训练等背景，把视觉、机器人和大型从零训练移出主体。

6. 用作业的三类理解标签呈现状态，不把L3的扩展等级、目标等级或“资料可支撑”等同于本组掌握程度。
7. 保留原计划的长期云服务器路线，提出更轻的第一版：文件维护、托管前端、服务端AI接口与自有域名；所有上线与费用仍需实际验收。
